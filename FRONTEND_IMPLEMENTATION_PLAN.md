# Frontend Implementation Plan

## Purpose

Build a receptionist-friendly frontend for the Home Credit default risk system.

The frontend should let a non-technical loan desk user enter applicant details, submit them to the serving API, and see a clear risk estimate. It should not feel like an ML engineering dashboard. Technical model details should exist, but stay secondary.

## Product Positioning

This frontend is an internal loan risk checking tool.

It is not:

- A public landing page
- A model training dashboard
- An MLflow replacement
- A final loan approval system

It is:

- A simple interface for scoring one applicant at a time
- A friendly wrapper around the existing FastAPI serving layer
- A demo-ready full-stack layer for the ML project
- A way to show model health and drift status without overwhelming the main user

## Primary User

The main user is a receptionist, loan desk operator, or non-technical staff member.

They should be able to:

- Fill in a familiar loan application style form
- Submit the application for a risk estimate
- Understand the result without knowing ML terminology
- Know whether the prediction system is currently usable

They should not need to understand:

- MLflow experiments
- Run IDs
- PSI formula
- Feature engineering
- Model artifact paths
- Full model feature vectors

## Core UX Principle

The frontend should answer three questions quickly:

1. Is the system ready?
2. What applicant details do I need to enter?
3. What is the risk estimate?

Everything else should be secondary.

## Backend APIs Used

The frontend will use the existing FastAPI backend.

```text
GET  /health
POST /predict
GET  /drift?min_records=50
```

Expected local backend URL:

```text
http://127.0.0.1:8000
```

### Important API Reality Checks

The endpoint names are correct, but the frontend must respect how the current backend actually behaves.

```text
GET /health
```

Returns HTTP 200 even when the model is degraded. The frontend must inspect the response body:

```text
model_loaded === true  -> Model Online
model_loaded === false -> Model Degraded
```

Do not treat HTTP 200 alone as proof that prediction is available.

```text
POST /predict
```

Accepts a flexible JSON object, and the backend explicitly requires four model-style fields:

```text
AMT_CREDIT
AMT_INCOME_TOTAL
DAYS_BIRTH
DAYS_EMPLOYED
```

The frontend should keep these four fields mandatory because they are human-available and required by the live API.

Frontend mandatory set:

```text
AMT_CREDIT
AMT_INCOME_TOTAL
DAYS_BIRTH
DAYS_EMPLOYED
```

The frontend must convert receptionist-friendly fields into these backend field names before sending the request.

Several other fields strongly improve feature quality because they feed autogenerated serving features:

```text
AMT_ANNUITY
EXT_SOURCE_1
EXT_SOURCE_2
EXT_SOURCE_3
```

These should be treated as recommended quality-improving fields, not hard blockers. A receptionist may not always know them at the time of scoring.

Reason:

- `AMT_CREDIT` and `AMT_INCOME_TOTAL` feed `CREDIT_INCOME_RATIO`
- `AMT_ANNUITY` and `AMT_INCOME_TOTAL` feed `ANNUITY_INCOME_RATIO`
- `AMT_CREDIT` and `AMT_ANNUITY` feed `CREDIT_TERM`
- `DAYS_EMPLOYED` and `DAYS_BIRTH` feed `DAYS_EMPLOYED_PERCENT`
- `EXT_SOURCE_1`, `EXT_SOURCE_2`, and `EXT_SOURCE_3` feed `EXT_SOURCE_MEAN`, `EXT_SOURCE_MIN`, and `EXT_SOURCE_PRODUCT`

Without the recommended fields, the current backend falls back unevenly:

- some derived features become `0.0`
- some become `NaN`
- then the derived feature itself gets median-filled later

That makes the final feature row less intuitive than it looks from the frontend. The UI should communicate this as estimate quality, not punish the user by blocking the flow.

```text
GET /drift?min_records=50
```

May return HTTP 503 when there are not enough recent predictions in the in-memory drift window. This is a normal state, not necessarily an application failure.

### Browser CORS Requirement

PowerShell can call the API directly, but a browser frontend is stricter.

If the frontend runs at:

```text
http://localhost:5173
```

and the backend runs at:

```text
http://127.0.0.1:8000
```

browser requests may be blocked unless CORS is configured.

Before connecting the real frontend, handle CORS using one of these options:

- Add FastAPI `CORSMiddleware` for the local frontend origin
- Or configure a Vite dev proxy so browser calls go through the frontend dev server

Recommended for this project:

- Add explicit FastAPI CORS support for local development origins
- Keep it restricted to known local origins, not `"*"` by default

## Form Strategy

Do not expose all 151 model features.

Also do not expose only a tiny handful of fields forever, because too many missing features would be filled with medians and many applicants would look artificially similar.

Use a four-part form strategy:

1. Required human fields always visible
2. Recommended quality fields shown as strongly suggested
3. Optional extras added progressively
4. Internal/derived fields never shown

### Required Human Fields

These should always be visible and always required:

```text
Age
Annual Income
Requested Loan Amount
Years Employed
```

`Customer ID` should stay visible, but optional. It is useful for tracking, not required for prediction.

Backend mapping:

```text
Age                   -> DAYS_BIRTH
Annual Income         -> AMT_INCOME_TOTAL
Requested Loan Amount -> AMT_CREDIT
Years Employed        -> DAYS_EMPLOYED
```

Tracking field mapping:

```text
Customer ID -> SK_ID_CURR
```

Conversion rules:

```text
DAYS_BIRTH = -age * 365
DAYS_EMPLOYED = -years_employed * 365
```

### Recommended Quality Fields

These should be visible near the required fields, but not hard-required:

```text
Annuity Amount
External Score 1
External Score 2
External Score 3
```

The UI should mark them as:

```text
Recommended for better estimate
```

not:

```text
Required
```

If these fields are missing, the frontend can still submit the request, but the result panel should show an estimate-quality note:

```text
Basic estimate: add annuity and external scores for a stronger check.
```

Backend mapping:

```text
Annuity Amount   -> AMT_ANNUITY
External Score 1 -> EXT_SOURCE_1
External Score 2 -> EXT_SOURCE_2
External Score 3 -> EXT_SOURCE_3
```

### Why These Fields Matter

These fields are not just useful raw inputs. They directly control autogenerated features created in serving:

```text
CREDIT_INCOME_RATIO
ANNUITY_INCOME_RATIO
CREDIT_TERM
DAYS_EMPLOYED_PERCENT
EXT_SOURCE_MEAN
EXT_SOURCE_MIN
EXT_SOURCE_PRODUCT
```

The current backend does not consistently "fill missing raw inputs first, then derive."

Instead it usually:

1. derives features from available raw inputs
2. produces `0.0` or `NaN` in some missing-input cases
3. median-fills the derived feature later

That means these driver inputs should be encouraged strongly, and the UI should explain estimate quality when they are missing.

Longer-term, the backend should be cleaned up so raw imputation and feature derivation are consistent. That would let the frontend stay simple without sacrificing model-row quality.

### Optional Fields Added Progressively

Optional fields should not appear all at once.

Instead, the UI should use an `Add input` control:

1. user clicks `Add input`
2. dropdown opens
3. dropdown shows only safe, user-enterable optional fields
4. fields are sorted by descending importance
5. once selected, that field appears in the form
6. selected fields disappear from the dropdown
7. selected optional fields can be removed

Safe optional fields for version 1:

```text
Goods Price
Gender
Owns Car
Owns Property
Number of Children
Family Members
```

The exact optional list must still be checked against `data/processed/feature_names.json` before implementation.

### Categorical Field Warning

Categorical frontend fields are risky because the backend currently expects already-encoded numeric model fields.

For example:

```text
CODE_GENDER: F -> 0, M -> 1
```

But the frontend should not blindly send strings like:

```text
"Male"
"Female"
"Married"
"Higher education"
```

unless the mapping is known and tested.

Version 1 should only include categorical fields where the encoding is explicit and stable:

```text
CODE_GENDER
FLAG_OWN_CAR
FLAG_OWN_REALTY
```

More complex label-encoded fields, such as family status or education type, should be delayed unless the backend exposes a reliable mapping.

Safer v1 optional fields:

```text
Goods Price
Gender
Owns Car
Owns Property
Number of Children
Family Members
```

Fields to postpone until mappings are exposed:

```text
Family Status
Education Type
Occupation Type
Income Type
Housing Type
```

## Input Mapping Rules

All human-friendly frontend fields must be mapped in one place:

```text
frontend/src/domain/inputMapping.ts
```

This avoids accidental inconsistent conversions.

Example responsibility:

```text
ageYears -> DAYS_BIRTH
employmentYears -> DAYS_EMPLOYED
loanAmount -> AMT_CREDIT
annualIncome -> AMT_INCOME_TOTAL
```

The UI should never scatter model-specific conversions across multiple components.

### Initial Payload Contract

The first version of the frontend should produce payloads shaped like this:

```json
{
  "SK_ID_CURR": 999999,
  "AMT_CREDIT": 500000,
  "AMT_INCOME_TOTAL": 150000,
  "DAYS_BIRTH": -15000,
  "DAYS_EMPLOYED": -2000
}
```

Recommended quality fields should be included when the user provides them:

```json
{
  "AMT_ANNUITY": 25000,
  "EXT_SOURCE_1": 0.45,
  "EXT_SOURCE_2": 0.5,
  "EXT_SOURCE_3": 0.62
}
```

Optional known-safe fields can be added after the mandatory flow works:

```json
{
  "AMT_GOODS_PRICE": 450000,
  "CODE_GENDER": 1,
  "FLAG_OWN_CAR": 1,
  "FLAG_OWN_REALTY": 0,
  "CNT_CHILDREN": 0,
  "CNT_FAM_MEMBERS": 2
}
```

## Validation Rules

Validation should happen before calling `/predict`.

Suggested rules:

```text
Age must be between 18 and 100
Annual income must be greater than 0
Loan amount must be greater than 0
Years employed must be 0 or greater
Years employed cannot be greater than age - 14
Annuity amount must be greater than 0 when provided
External scores 1, 2, and 3 must be between 0 and 1 when provided
Number of children cannot be negative
Family members cannot be negative
```

Validation messages should be plain and helpful.

Example:

```text
Please enter an annual income greater than 0.
```

Avoid technical messages like:

```text
AMT_INCOME_TOTAL validation failed.
```

## Prediction Result Design

The model returns a probability.

The frontend should present this as a risk estimate, not a final decision.

Use wording like:

```text
Risk Estimate
Needs Review
Estimated default probability: 40.1%
```

Avoid wording like:

```text
Reject
Unsafe customer
Bad applicant
```

### Risk Labels

The dataset has an approximate default rate around 8%, so a probability like 40% is already very high.

Initial display thresholds:

```text
Low Risk:       < 10%
Needs Review:  10% to 25%
High Attention: > 25%
```

These are UI interpretation thresholds only. They are not official credit policy.

Later improvement:

- Derive thresholds from validation prediction percentiles
- Add business-approved threshold configuration
- Show rank/percentile instead of only raw probability

## Health Status

On page load, call:

```text
GET /health
```

Show a small status badge:

```text
Model Online
Model Offline
Model Degraded
```

If healthy, show:

```text
Ready
Production model loaded
```

If unhealthy, show:

```text
Prediction service unavailable
```

The form can stay visible, but the submit button should be disabled when the backend is unavailable.

Important:

`/health` may return HTTP 200 with `status: "degraded"` and `model_loaded: false`.

Frontend health logic must use the response body, not just the HTTP status code.

## Drift Status

Drift should not dominate the receptionist UI.

Show only a simple system signal by default:

```text
System Normal
System Needs Technical Review
Not enough recent checks yet
```

Use `/drift` behind the scenes.

For local demos:

```text
GET /drift?min_records=1
```

For more realistic use:

```text
GET /drift?min_records=50
```

PSI values should appear only in a collapsed technical details section.

Important:

`/drift` returning HTTP 503 can be normal if the rolling window has fewer records than `min_records`.

The frontend should map this case to:

```text
Not enough recent checks yet
```

not:

```text
System error
```

Also, `/drift` can trigger alert logging when PSI crosses the threshold. Do not poll it aggressively. Prefer one of these patterns:

- Call drift after a successful prediction
- Add a manual refresh button in technical details
- Poll slowly only in an admin-style view

For the receptionist UI, avoid frequent automatic polling.

## Technical Details Section

Keep this collapsed by default.

It can include:

```text
Model version
Request ID
Raw default probability
Drift alert true/false
Records evaluated for drift
Top PSI values
```

Do not include MLflow run history in version 1.

MLflow belongs to the model operations side, not the receptionist workflow.

## Error Handling

The frontend should handle these cases:

- Backend not running
- Model not loaded
- Browser CORS blocked
- Missing required input
- Invalid input values
- Prediction endpoint returns 422
- Prediction endpoint returns 500
- Drift endpoint returns 503 because there are not enough records

User-facing messages should be simple:

```text
Could not reach the prediction service. Please check that the backend is running.
```

```text
The model is not ready yet. Please try again after the service finishes starting.
```

```text
Not enough recent predictions to check system drift yet.
```

If the browser reports a failed request while the backend is running, CORS should be checked before assuming the API is broken.

## Known Tradeoffs

This frontend will not ask for all model features.

That improves usability, but may reduce prediction specificity because missing features are filled by the backend using medians/defaults.

To reduce this tradeoff:

- Keep only the human-available API-required fields mandatory
- Mark hard-to-know driver fields as recommended
- Add optional fields progressively
- Prefer important human-enterable raw fields
- Avoid showing all engineered columns
- Avoid categorical fields unless mappings are known

The current serving logic derives some features before all missing raw inputs are imputed.

That means leaving a derived-feature driver blank can lead to odd backend behavior:

- some derived values become `0.0`
- some become `NaN`
- then the derived feature is median-filled later

To reduce this tradeoff:

- show estimate-quality messaging when recommended fields are missing
- do not expose derived fields directly
- consider cleaning up serving logic later so raw-field imputation and feature derivation are more consistent

This frontend will show drift only as a system status.

That improves receptionist usability, but hides technical detail.

To reduce this tradeoff:

- Keep PSI values in the technical details panel
- Do not put PSI charts in the main workflow

The browser frontend needs CORS or a development proxy.

That adds one small backend/dev-server concern before API calls work in the browser.

To reduce this tradeoff:

- Configure explicit local origins
- Do not use open wildcard CORS unless it is only for temporary local development
